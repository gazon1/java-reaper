# java-reaper

Рейпер застаревших Gradle/Kotlin-демонов: находит процессы, за которыми никто
не следит, и закрывает их. Самостоятельный инструмент рабочей машины —
репозиторий проекта он не трогает.

**Памятка при авариях — [RUNBOOK.md](RUNBOOK.md).**

## Проблема

На машине 10–13 Gradle/Kotlin-демонов держали 23.2 ГБ. Штатный 3-часовой
idle-таймаут Gradle на практике не работает: за 14 дней накопились демоны с
простоем **до 12 суток** (последняя сборка 2026-10-07, процесс жив до сих пор).
Kotlin-демон умеет застревать навсегда: `CompileServiceImpl.kt` считает клиента
живым **только по факту существования маркер-файла**
(`aliveFlagPath?.let { File(it).exists() } ?: true`), без проверки процесса.
Маркер клиента создаётся через `Files.createTempFile(...)` + `deleteOnExit()`, то
есть переживает SIGKILL клиента; после этого демон не выходит ни через «нет
клиентов», ни через idle-таймаут (ветка проверяется только при
`Aliveness.Alive`, а демон уже в `LastSession`).

## Цели: какие программы мы убираем

**Цель** (target) — описание одного вида демонов: как его узнать среди прочих
процессов, где его лог, как по логу понять, что он работал, сколько ждать
простоя и кого он защищает.

Описание целей лежит в `~/.config/java-reaper/targets.yaml` (YAML). Файл
необязателен: без него работают встроенные цели Gradle и Kotlin — ровно как
раньше. Файл переопределяет встроенные цели по имени и может добавлять новые.

```yaml
version: 1

targets:
  - name: gradle
    label: Gradle
    match_cmdline: "org.gradle.launcher.daemon.bootstrap.GradleDaemon"
    log_name_regex: '^daemon-\d+\.out\.log$'
    activity: markers            # или mtime
    build_start: "Received command: Build"
    build_end: "Marking the daemon as idle"
    cancel: "client disconnection detected"
    idle_seconds: 21600
    recreate_cost_seconds: 40
    self_timeout_seconds: 10800
    protects: [kotlin]
    rebuildable: true
```

| поле | что означает |
|---|---|
| `match_cmdline` | подстрока в cmdline процесса, по которой мы его узнаём |
| `log_name_regex` | регулярка на имя файла лога (лог ищем среди открытых fd `/proc/PID/fd` — точно, без эвристик) |
| `activity` | `mtime` — активность это время последней записи в лог; `markers` — активность это маркеры начала/конца работы в тексте лога |
| `build_start` / `build_end` / `build_end_alt` / `cancel` | маркеры для `activity: markers` |
| `idle_seconds` | порог простоя: сколько ждать, прежде чем убирать |
| `recreate_cost_seconds` | цена холодного старта: влияет на **порядок** уборки, не на сам факт |
| `self_timeout_seconds` | через сколько демон умирает сам (у Gradle 180 мин: наш порог обязан быть выше, иначе мы конкурируем с Gradle за одни и те же демоны) |
| `protects` | какие виды демонов этот вид защищает, пока сам работает |
| `rebuildable` | «это пересоздаваемый кэш, его можно убить» |

### Как добавить новую программу

1. Описать цель в `~/.config/java-reaper/targets.yaml` (для программы без
   своих маркеров достаточно `activity: mtime` — это самый простой случай);
2. **измерить порог**, а не выбрать его: собрать историю
   (`python3 tools/prune-logs.py --archive-only --min-age-hours 0`) и
   прогнать `tools/simulate.py` по ней. Неизмеренный порог — это наугад;
3. сначала понаблюдать в dry-run (`java-reaper --status`) — сколько памяти
   держит цель и кого рейпер считает кандидатом;
4. и только потом — kill-режим.

**Чего файл целей не покрывает:** смысл самих правил политики, умение
читать логи и таймстемпы, всё про сигналы и безопасность. Это остаётся в
коде — конфигурировать его нельзя, и не нужно: правила должны быть одни и
те же для всех целей, иначе их невозможно сравнивать.

### Кто главнее: плоский конфиг или targets.yaml

| что | где живёт | приоритет |
|---|---|---|
| порог простоя вида | `targets.yaml` → `idle_seconds`; плоский ключ `IDLE_SECONDS` / `KOTLIN_IDLE_SECONDS` | **явно заданный плоский ключ главнее**; если он не задан — берётся YAML; если нет и его — значение по умолчанию |
| цена воссоздания | `targets.yaml` → `recreate_cost_seconds`; плоский `GRADLE_RECREATE_COST_SECONDS` / `KOTLIN_RECREATE_COST_SECONDS` | так же |
| всё остальное (память, свипы, флаги, критерий пилота) | плоский конфиг | только он |

Плоский ключ главнее не из упрямства: оператор десятилетиями правил
`IDLE_SECONDS` в своём конфиге, и тихо перестать его учитывать — ловушка.
Но если ключ и значение в YAML **расходятся**, рейпер предупреждает об этом
при каждом запуске: молчать об этом нельзя, иначе «опечатка в конфиге»
выглядит как «рейпер сломался».

### Зависимость

Для чтения `targets.yaml` нужен PyYAML (`pip install -r requirements.txt`).
Без него рейпер работает и использует встроенные цели, но предупреждает об
этом при каждом запуске.

## Как принимаются решения

Простой определяется **по логу**, а не по сокетам и не по возрасту процесса:

| класс | признак простоя | признак занятости |
|---|---|---|
| Gradle | последняя отметка `Marking the daemon as idle` (демон освободился) | `Received command: Build` новее конца ⇒ сборка идёт |
| Kotlin | mtime его собственного лога | лог обновлялся недавно |

Почему не сокеты: у компилирующего Kotlin-демона число established-соединений
колеблется 8→4→0→0 за 75 секунд. Наличие соединения — это защита, отсутствие
ничего не доказывает.

Почему не mtime лога Gradle: **простаивающий демон пишет в лог постоянно** —
DEBUG-спам вида `Waiting to acquire shared lock on daemon addresses registry`
идёт примерно 124 Б/с, то есть ~10 МБ в сутки на демон. Замер: лог демона
2178880 вырос с 9 609 679 до 9 632 035 байт за 3 минуты, тогда как логи
Kotlin-демонов за то же время не изменились ни на байт. Поэтому у Gradle
признак простоя — маркер в тексте лога, а у Kotlin — mtime (у Kotlin лог в
простое не растёт).

Разбор лога Gradle инкрементальный: при первом свипе файл читается целиком
(до `LOG_SCAN_MAX_BYTES`), дальше — только новые байты, смещение хранится в
состоянии. Так маркеры находятся точно и свип остаётся быстрым (≈0.4 с на
8 демонов) несмотря на спам.

Маркер конца сборки выбран INFO-уровневый (`Marking the daemon as idle`): он
встречается ровно 1:1 со сборками в версиях Gradle 8.10, 8.14.6 и 9.7.1
(проверено: 361/361, 128/128, 8/8). Запасной `after build finished` — DEBUG-уровень
и исчезает при выключенном DEBUG-логировании.

### Правила (таблица, а не ветвления)

Правила живут в `reaper/policy.py` и применяются по приоритету; первое
совпавшее решает. Базовый принцип: **неизвестное ⇒ оставить**.

Каждое правило — объект с описанием: `doc` (что значит по-человечески),
`condition` (формальное условие), следствиями (`busy`, `protected`) и
предикатом `check`. Таблица читается как спецификация, и её можно
напечатать:

```bash
java-reaper --explain
```

| правило | действие |
|---|---|
| `allowlist` | оставить (PID вне `PID_ALLOWLIST`) |
| `no-log` | оставить, защищён (лог не найден) |
| `unknown-history` | оставить, защищён (лог не разобран) |
| `no-baseline` | оставить, защищён (первый свип) |
| `peer` | оставить, защищён (наблюдатель) |
| `cpu-busy` | оставить, занят (CPU за свип > `BUSY_CPU_SECONDS`) |
| `children` | оставить, занят (живой ребёнок) |
| `recent-log` | оставить, занят (лог обновлялся недавно) |
| `small-footprint` | оставить (footprint < `MIN_FOOTPRINT_MB`) |
| `stuck` | убить (завис: клиент отвалился во время сборки, прошло > `STUCK_AFTER_SECONDS`) |
| `building` | оставить, занят (сборка идёт) |
| `not-idle` | оставить (простой < порога простоя своего класса) |
| `protected-by-build` | оставить, защищён (идёт свежая сборка другого вида — они сейчас нужны) |
| `memory-not-needed` | оставить (памяти хватает, а демон небольшой) |
| `kill` | убить |

Защита **не** сбрасывает отсчёт простоя: сбрасывает его только реальная
наблюдённая активность (CPU, дети, свежий лог). Иначе демон, за которым
подключён кто-то постоянно, не состарился бы никогда.

Ignore-список детей сверяется **по имени исполняемого файла**, а не по
подстроке во всём cmdline: подстрочный поиск ловил classpath-пути вроде
`…playwright-1.49.0.jar` и помечал реально работающий fork приложения как шум
(демон 3661782 терял защиту).

Peer-сокеты: учитываются только **локальные** соединения. Исходящие HTTPS
(34.36.x.x:443) клиентом не являются — раньше они давали ложную защиту.
Соединение старше `PEER_MAX_AGE_SECONDS` (по умолчанию 6 ч) считается
зависшим клиентом и защиту не даёт: демон, к которому вечно подключён
мёртвый IDE, иначе не состарился бы никогда.

Два idle-демона, ссылающиеся друг на друга, **не** защищают друг друга
(least fixed point снизу вверх).

Эскалация «зависшей сборки»: старт без конца + нет CPU + нет детей + нет
клиентов дольше порога простоя ⇒ кандидат. Иначе демон с умершим клиентом был бы
бессмертен.

Отдельно — правило `stuck`: клиент отвалился именно во время сборки
(`client disconnection detected, canceling the build`), сборка не завершилась —
работать некому, и работать уже некому. Такой демон Gradle не убирает: его
idle-таймаут не действует, пока демон «в сборке». Свой порог
`STUCK_AFTER_SECONDS` (1 ч) — ждать шесть часов демон, которому работать
некому, незачем; демон с живым клиентом защищён правилом `peer` раньше.

Тонкость формата: строка отмены в логе Gradle идёт **без таймстемпа** (это
часть стектрейса) — проверено на 97 строках в 80 логах. Поэтому моментом
отмены считается начало той сборки, во время которой клиент отвалился (её
старт парсится всегда). Раньше код искал таймстемп в строке отмены и не
находил никогда — то есть правило на живых данных не срабатывало ни разу.

Признак переживает перезапуск рейпера: момент отмены хранится в состоянии, а
новая сборка после отмены обесценивает её (клиент вернулся — демон не завис).

Взаимодействие классов: если хоть у одного Gradle-демона идёт **свежая**
сборка, **все** Kotlin-демоны защищаются — иначе компилятор может умереть
посреди сборки. «Свежая» — начавшаяся не позже `GRADLE_BUILD_ACTIVE_SECONDS`
назад (30 мин): сборка, начавшаяся несколько часов назад и не завершившаяся, —
это зависший демон, а не идущая работа. Без этого ограничения один
зависший Gradle-демон блокировал бы уборку всех Kotlin-демонов навсегда
(он вечно «в сборке»).

### Контекст: что видно только вместе со всеми демонами

Часть признаков невозможно узнать по одному демону: сколько памяти доступно
системе и идёт ли где-то сборка Gradle. Это и есть **контекст** —
отдельный объект (`reaper/model.py: Context`), а не поля в признаках демона.

Почему отдельный объект, а не ещё два поля: когда «сборка идёт» лежало рядом
с признаками одного демона, оно означало «последняя сборка не завершилась» —
а у зависшего демона это верно навсегда. Один зависший Gradle-демон
блокировал уборку всех Kotlin-демонов, и правило в итоге работало «навсегда
против себя».

Контекст собирается один раз на свип (`reaper/classify.py: build_context`)
и попадает в `Signals.context`, а оттуда — в `Decision.context` и в JSON.
В тестах контекст передаётся явно, поэтому решение не зависит от того,
сколько памяти свободно на машине, где идут тесты.

### Давление по памяти

Рейпер существует ради памяти. Если свободной памяти достаточно, убивать
небольшого простаивающего демона — это только цена (холодный старт) без
выгоды. Отсюда правило `memory-not-needed`:

- источник — `MemAvailable` из `/proc/meminfo` (учитывает кеш, который можно
  вытеснить без обмена; честнее, чем `MemFree`);
- если свободно **меньше** `MEMORY_PRESSURE_MB` (4 ГБ) — машине память
  нужна, демоны подлежат уборке;
- если свободно **больше** порога — демоны меньше `KILL_LARGE_DAEMON_MB`
  (4 ГБ) не трогаются: убирать их незачем;
- крупные демоны (≥ `KILL_LARGE_DAEMON_MB`) убираются в любом случае:
  столько памяти жалко держать простаивающим;
- память измерить не удалось — ведём себя как раньше (не как «памяти много»);
- `MEMORY_PRESSURE_MB=0` — режим «всегда убирать» (используется в тестах
  для детерминизма и как осознанный выбор оператора).

На живой машине это 34 ГБ доступных при 19 ГБ в демонах: то есть сейчас
уборка крупных демонов — единственное, что вообще имеет смысл.

### Порядок уборки: цена ошибки

Цена ошибки в правилах — это цена **холодного старта** демона, которого мы
убили зря. Измерено: Gradle — 41.6 с против 2.4 с тёплого; Kotlin дешёв
(это просто старт JVM).

Цена влияет не на **факт** уборки, а на **порядок**: сначала убирается тот,
кто даёт больше освобождённой памяти на секунду потраченного времени
(`reaper/execute.py: kill_order`). Дешёвый Kotlin-демон уступает дорогому
Gradle-ному. При равной выгоде Gradle идёт первым: его shutdown-hook чистит
маркеры клиентов, и это надо сделать раньше, чем ляжет Kotlin-демон.

Ключи: `GRADLE_RECREATE_COST_SECONDS`, `KOTLIN_RECREATE_COST_SECONDS`.

## Политика сигналов

- `SIGTERM` — пакетом всем подтверждённым кандидатам, затем одна пауза
  `GRACE_SECONDS`.
- Kotlin-демон, не вышевший за grace → `SIGKILL` (клиент мёртв, фантом-маркер не
  создаётся).
- Gradle-демон, не вышевший → счётчик попыток; после `GRADLE_SIGKILL_AFTER_TRIES`
  неудач → `SIGKILL`. Счётчик обнуляется, если демон снова стал занят **или
  защищён** (иначе накопится за несвязанные эпизоды и убьёт живой демон).
- Сигналы отправляются только через `pidfd` (`os.pidfd_open` +
  `signal.pidfd_send_signal`), поэтому не могут попасть в переиспользованный PID.
  Порядок: `stat` → `pidfd_open` → повторный `stat`.
- **Лимит `MAX_KILLS_PER_SWEEP`** (по умолчанию 3): страховка от массовой ошибки
  правил. Остальные кандидаты в этом свипе помечаются «превышен лимит».
- **Аварийный тормоз**: файл `~/.config/java-reaper/disabled` останавливает
  рейпер до любых действий.

## Почему пороги такие

Порогов два, и они **не ниже**, а выше, чем предполагалось изначально.

### Gradle: 6 ч (а не 3 и не 1)

У Gradle есть **собственный** idle-таймаут: `idleTimeout=10800000` мс =
**180 мин**. В логах это видно прямо: `Daemon will be stopped at the end of
the build after being idle for 180 minutes`. Gradle убивает демона
проактивно — из 30 демонов, умерших с idle-маркером, **все 30** умерли
ровно через 3.0007 ч после последней сборки, и ни один из них не успел
начать новую.

Значит, порог рейпера обязан быть **выше** 180 мин: иначе мы конкурируем с
Gradle за одни и те же демоны и проигрываем — к моменту нашего свипа демон
уже мёртв.

Ниже 3 ч опускаться нельзя. Ретроспективно по 8291 простою между сборками:

| порог | доля ложных срабатываний (демон понадобился снова) |
|---|---|
| 60 мин | 88.5 % |
| 90 мин | 92.9 % |
| 120 мин | 100 % |
| 180 мин | 0 % (но там уже работает таймаут Gradle) |

При 6 ч остаются **только зависшие** демоны — клиент отвалился во время
сборки (`client disconnection detected, canceling the build`, 247 логов),
сборка не завершилась, и Gradle такой демон не убирает. За всю историю
таких 3 из 893, и все три убил наш рейпер (простой 52.7 / 61.2 / 107.3 ч,
в логах — `Runtime.exit() called with status: 143`).

Причины смерти 893 демонов с idle-маркером:

| причина | доля |
|---|---|
| клиент отключился / teardown сразу после сборки | 834 (93.4 %) |
| таймаут Gradle (~3 ч) | 30 (3.4 %) |
| пережил таймаут (завис) | 3 (0.3 %) |
| прочее | 26 (2.9 %) |

### Kotlin: 2 ч — отдельный порог, отдельная цель

У Kotlin-демона **нет своего idle-таймаута**: он умирает только по
`No more clients left` (в 125 из 209 логов есть `Shutdown complete` /
`Delayed shutdown`). То есть его не убирает никто — это и есть настоящая
цель рейпера, а не «подчистка за Gradle».

Порог 2 ч заведомо выше «живого» простоя: между сессиями компиляции
p99 = 16 мин, p99.9 = 100.6 мин, максимум 1.7 ч (938 промежутков).
Признак простоя — mtime его лога: в простое лог Kotlin не растёт (0 Б/с
за 20 с), тогда как Gradle пишет ~124 Б/с DEBUG-спама.

На момент обследования: 2 Kotlin-демона держали 6.7 ГБ; 207 из 209 логов
Kotlin были неактивны дольше 3 ч, 149 — дольше 24 ч, суммарно 106 МБ.

### Окно «понадобился снова»: 6 ч

`REUSE_WINDOW_SECONDS` — окно, в котором «убитый» демон, понадобившийся
снова, считается ложным срабатыванием. Измерено: демон возвращается с
лагом p50 = 0.2 ч, p90 = 6.4 ч, max = 25.1 ч. При окне 2 ч мы видели бы
лишь 61 % возвратов (4 ч — 67 %, 8 ч — 97 %), то есть занижали долю ложных
срабатываний почти вдвое. Окно 6 ч.

### Смена правил обнуляет метрику

Метрика пилота измеряет долю ложных срабатываний для **конкретных** правил
и порогов. Поэтому при смене правил (`RULES_VERSION` в `reaper/config.py`)
метрика сбрасывается: события, набранные по старым порогам, измеряют другое.
Сброс происходит автоматически перед свипом, о чём рейпер пишет в вывод.

История версий:

| версия | что изменилось | метрика |
|---|---|---|
| 3 | правило «зависший» и защита Kotlin по свежей сборке Gradle | обнулена |
| 4 | правило `memory-not-needed` (уборка зависит от свободной памяти) + защита «идёт сборка Gradle» только по свежей сборке (`GRADLE_BUILD_ACTIVE_SECONDS`) | обнулена |

Имя правила `gradle-building` в версии 4 заменено на `protected-by-build`:
отношение «Gradle защищает Kotlin» стало общим («этот вид защищает те виды,
что перечислены в `protects`»), и имя перестало называть конкретную программу.
**Решения при этом не изменились** — это проверяется тестом
`tests/test_targets.py: TestBehaviorUnchanged`, который сравнивает решения по
демонам с файлом целей и без него. Метрика пилота измеряет решения, а не
имена правил, поэтому сбрасывать её из-за переименования не нужно.

## Установка

```bash
ln -sfn ~/dev/java-reaper/java-reaper ~/.local/bin/java-reaper
mkdir -p ~/.config/java-reaper
cp ~/dev/java-reaper/config.example ~/.config/java-reaper/config
cp ~/dev/java-reaper/targets.example.yaml ~/.config/java-reaper/targets.yaml
cp ~/dev/java-reaper/config.env.example ~/.config/java-reaper/env
pip install --user -r ~/dev/java-reaper/requirements.txt   # PyYAML: файл целей
mkdir -p ~/.config/systemd/user
cp ~/dev/java-reaper/systemd/java-reaper.{service,timer} ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now java-reaper.timer
```

Режим выкатки задаётся `~/.config/java-reaper/env` (`REAPER_ARGS=--mode=dry-run`
на время пилота, `--mode=kill` — после проверки метрики). По умолчанию в юните
стояит `--mode=dry-run`: боевой режим включается только явно.

`loginctl enable-linger` **обязателен**: `Linger=no`, а `KillUserProcesses` не
задан (дефолт `no`) — демоны переживают логаут, пользовательский таймер нет.
Команда требует пароль администратора (`polkit` → `auth_admin_keep`), поэтому
её выполняет владелец машины.

Если `systemctl --user start` зависает, а `systemctl --user list-jobs` показывает
job'ы в состоянии `waiting` — завис сам user-менеджер. На этой машине он
попался в busy-loop (1 поток, ~96 % одного ядра, `daemon-reload` отвечает, job'ы
не выполняются). Лечится без остановки юнитов:

```bash
systemctl --user daemon-reexec
```

## Режимы

```bash
java-reaper --status           # таблица демонов с решениями, ничего не меняет
java-reaper --status --json    # то же машинно-читаемо
java-reaper --health           # «таймер молча не работает?» + метрики
java-reaper --pilot            # вердикт по пилоту: можно ли включать kill-режим
java-reaper --audit            # демоны с простоями длиннее IDLE_SECONDS (критерий приёмки)
java-reaper --explain          # таблица правил политики: что, условие, следствие
java-reaper --mode=dry-run     # решения + запись событий «would kill» для метрики
java-reaper --mode=kill        # исполнение
```

`--dry-run` — краткий синоним `--mode=dry-run`. `--status`, `--audit`, `--pilot`,
`--health`, `--explain` — команды только на чтение: состояние не трогают,
baseline пишет только рабочий свип.

Первый свип ничего не убивает (нет baseline) — это нормально. Второй свип уже
принимает решения.

### Коды возврата

Команды читают состояние и потому пригодны для проверок в cron/CI:

| команда | 0 | 1 | 2 |
|---|---|---|---|
| `--pilot` | можно включать kill-режим | нельзя (доля ложных срабатываний выше критерия) | данных мало |
| `--audit` | демонов с простоями сверх порога нет | есть (критерий приёмки не выполнен) | — |
| `--health` | свипы идут | свипов не было / таймер молчит | — |

### Контракт машинного вывода (`--json`)

Каждый JSON-документ содержит `schema_version` — версию формата. Потребитель
обязан проверять её: при смене версии поля меняются, и «поле пропало» должно
быть ошибкой, а не тихим нулём.

Текущая версия: `3` (`JSON_SCHEMA_VERSION` в `reaper/report.py`).

Схема 3 не изменилась после появления целей (targets.yaml): набор целей
меняет то, *какие* демоны видны, но не форму вывода. В `--status --json`
добавилась секция `targets` — описание целей (подпись, порог простоя, цена
воссоздания, модель активности, кого защищает) — чтобы потребитель видел,
по каким правилам считалось.

В версии 3 добавлены: секция `memory` (`available_mb`, `pressure_mb`,
`large_daemon_mb`), поля `rule` (какое правило сработало) и
`recreate_cost_seconds` (цена воссоздания) в записи демона, а также
`would_free_pending_mb`, `rule_hits`, `rule_hits_last`, `measured_count` и
`degradation` в корне документа. В версии 2 появились секция `kinds`
(сводка по классам демонов: сколько демонов, сколько памяти, кого под
удар, и какой порог простоя у класса), ключ `config.KOTLIN_IDLE_SECONDS`,
поля `stuck_build` и `canceled_at` в записи демона. В `--audit --json` поле
`idle_limit_seconds` стало объектом по классам
(`{"gradle": …, "kotlin": …}`) — раньше было одним числом.

| документ | ключевые поля |
|---|---|
| `--status --json` | `schema_version`, `now`, `config`, `targets`, `kinds`, `memory`, `daemons[]`, `metric`, `rule_hits`, `rule_hits_last`, `measured_count`, `degradation`, `freed_mb`, `would_free_mb`, `would_free_pending_mb`, `last_sweep_at`, `pilot_started_at`, `stale_peer_events`, `stale_peer_daemons`, `actions[]` |
| `--pilot --json` | `schema_version`, `metric`, `events`, `reused`, `reuse_rate`, `pilot_started_at`, `freed_mb`, `would_free_mb`, `stale_peer_events`, `criterion`, `verdict_code` |
| `--audit --json` | `schema_version`, `idle_limit_seconds` (объект по классам), `stale_daemons[]`, `total_footprint_mb`, `verdict_code` |

Запись одного демона (`daemons[]`): `pid`, `kind`, `footprint_mb`, `rss_mb`,
`swap_mb`, `idle_seconds`, `action`, `reason`, `busy`, `protected`,
`protectors[]`, `stale_peers[]`, `children`, `ignored_children`, `peers[]`,
`log_path`, `stuck_build`, `canceled_at`, `recreate_cost_seconds`, `rule`.

Приватность: в `--json` нет ни UID, ни внутренних путей пользователя; есть
только `log_path` (путь к логу демона — он и так лежит в `/proc/PID/fd`) и
числовые характеристики.

### Версия состояния

`state.json` версионируется (`STATE_VERSION`, сейчас 2). При смене версии
состояние мигрируется: неизвестные и мёртвые поля вычищаются, известные —
сохраняются. Миграция не теряет `peer_first_seen`: без него возраст
peer-соединения обнулялся бы при каждом перезапуске, и правило «зависший
клиент» (6 ч) никогда бы не срабатывало.

### Сторож вне user-менеджера

Таймер живёт в `systemd --user`, а user-менеджер на этой машине уже зависал
(busy-loop, ~96 % ядра) — тогда молча пропадают все user-юниты. Сторож
работает через `crond` (системный сервис) и потому переживает такую смерть.

```bash
# ~/.config/java-reaper/disabled не создан — сторож работает
crontab -l | grep java-reaper
*/5 * * * * /usr/bin/python3 ~/dev/java-reaper/tools/watchdog.py \
    >> ~/.local/state/java-reaper/watchdog.log 2>&1
```

Сторож делает две вещи: проверяет, что свипы идут (последний свип не старше
двух интервалов), и, если рейпер замолчал, выполняет свип сам. Аварийный
тормоз (`~/.config/java-reaper/disabled`) действует и на сторожа: он молчит и
ничего не чинит. Коды возврата: `0` — всё в порядке (или починил сам),
`1` — починить не удалось, `2` — рейпер отключён флагом.

### Месячный отчёт

```bash
python3 tools/monthly-report.py            # за 30 дней
python3 tools/monthly-report.py --days 7 --json
```

Собирает из `state.json`, `kills.jsonl` и **журнала свипов**
(`sweeps.jsonl`): освобождённую память, число и причины убийств, долю ложных
срабатываний (демон понадобился снова) и счётчик правила «зависший клиент».

Журнал свипов — это и есть непрерывное измерение эффекта: сколько памяти в
каждом свипе висело **под ударом** (`would_free_mb`), а не «сколько демонов
убито» (их всегда мало, а памяти — много). Отчёт показывает максимум и
среднее «под ударом» за период, текущий footprint по классам и гистограмму
сработавших правил.

### История демонов и симулятор правил

Пилот — это 7 дней ожидания и 8 накопленных событий ради ответа на вопрос
«сколько ложных срабатываний у наших правил». **Симулятор отвечает на тот же
вопрос по всей накопленной истории — за минуты.**

Данные для него — компактные сводки по демонам (`reaper/history.py`), которые
`tools/prune-logs.py` сохраняет **перед удалением** логов, в
`~/.local/state/java-reaper/logs-history.jsonl`. Сводка — это жизнь демона:
когда жил, когда шли сборки, была ли отмена. Килобайты вместо мегабайт;
история не исчезает вместе с мусором.

```bash
# собрать историю, ничего не удаляя
python3 tools/prune-logs.py --archive-only --min-age-hours 0

# прогнать текущие правила по всей истории
python3 tools/simulate.py

# чувствительность к порогу простоя
python3 tools/simulate.py --thresholds "30,60,120,180,240,360"

# чувствительность к порогу «зависшего» (его тоже надо измерять)
python3 tools/simulate.py --stuck-thresholds "15,30,60,120,240"
```

Модель знает про пороги простоя, порог зависших и то, что **Gradle убивает
демонов своим idle-таймаутом сам** (порог выше 180 мин для Gradle
бессмыслен — демона к нашему свипу уже не будет). Не знает про размер,
клиентов и CPU — поэтому убийств получается **верхняя оценка**, а доля ложных
срабатываний — консервативная.

Два независимых скана:

- `--thresholds` — порог простоя: сколько демонов переживёт застой;
- `--stuck-thresholds` — порог «зависшего»: зависшие демоны — отдельная
  популяция, их убирает рейпер, а не Gradle, значит порог должен быть
  **измерен**, а не выбран на глаз. Скан показывает, сколько зависших пережило
  порог (то есть было бы убито), долю ложных и сколько зависшие живут в
  среднем и в худшем случае.

Замер по корпусу (4.2 сут, 1106 демонов, 71 зависший Gradle): медиана жизни
после отмены — 2 мин, максимум 3.1 ч; порог 1 ч ловит **одного** демона из
71, ложных срабатываний ноль. То есть правило «зависший» сегодня почти
стреляет в пустоту — и это надо знать, а не считать, что оно работает.

**Честное слепое пятно**: у Kotlin-демона лог замолкает в момент последней
активности, поэтому момент его смерти из лога не виден — простой Kotlin
не измеряется вовсе. Чтобы это починить, рейпер отмечает момент, когда
заметил пропажу демона (`death_observed_at` в сводке), и дальше простой
считается до него. Отметка появляется в записях, сделанных после 2026-10-20;
старые записи корпуса этого не содержат.

Первый прогон по корпусу (4.2 сут, 1005 демонов):

| класс | порог | убито | ложных | доля |
|---|---|---|---|---|
| Gradle | 30 мин | 14 | 10 | 71 % |
| Gradle | 60 мин | 10 | 4 | 40 % |
| Gradle | 120 мин | 8 | 1 | 12 % |
| Gradle | 180 мин и выше | 1 | 0 | 0 % |
| Kotlin | любой | 0 | 0 | — (в корпусе всего 16 записей) |

Gradle-сторона по ЧИСЛУ убийств почти бесполезна: после 180 минут простоя
Gradle убирает демона сам, и до нашего свипа он не доживает. Ловится только
«зависший» (71 демон с отменой, из них единицы переживают час). Ценность
этой стороны — в памяти, а не в числе: каждый такой демон держит гигабайты.

Kotlin-сторона в корпусе пока не измерена: `/tmp` был очищен перезагрузкой,
логи Kotlin-демонов за прежние дни потеряны. История начнёт копиться сама
(сводка пишется при каждой уборке) — и тогда симулятор даст по ней честную
цифру.

### Архивирование умерших демонов самим рейпером

Логи Kotlin-демонов живут в `/tmp` и исчезают при перезагрузке. Если ждать,
пока кто-то уберёт мусор, сводка пропадёт вместе с файлом — и демон исчезнет
из истории навсегда.

Поэтому рейпер сам архивирует демонов, которых больше нет: на каждом свипе
он сверяет список живых демонов с состоянием и, найдя пропавшего, сохраняет
сводку по его логу в `~/.local/state/java-reaper/logs-history.jsonl` — пока
файл ещё жив (`reaper/cli.py: archive_vanished`).

Два важных следствия:

- **момент пропажи — это момент смерти демона** (`death_observed_at` в
  сводке). Лог-то замолчал давно, и без этой отметки простой демона вообще
  не виден: демон «умирает» вместе с последней записью в логе. Именно эта
  отметка делает Kotlin-сторону измеримой (см. слепое пятно выше);
- **повторов не будет**: сводка пишется один раз на демона (запись исчезает
  из состояния), а `tools/prune-logs.py` отбрасывает пути, уже сохранённые
  (`history_keys` — ключ «путь + mtime»), так что история не засоривается
  копиями.

### Уборка мёртвых логов

Gradle и Kotlin не убирают свои логи: `~/.gradle/daemon` — 1.2 ГБ (3870
файлов), `/tmp/kotlin-daemon*.log` — 108 МБ (207 файлов).

```bash
python3 tools/prune-logs.py                     # план (dry-run), ничего не удаляет
python3 tools/prune-logs.py --apply             # удалить
python3 tools/prune-logs.py --min-age-hours 24 --json
```

Что считается «логом мёртвого демона»:

- **файл не открыт ни одним процессом** — главная проверка: пока демон жив,
  он держит свой лог открытым;
- для Gradle дополнительно сверяется PID из имени (`daemon-<pid>.out.log` —
  там PID настоящий) с живым процессом-демоном;
- для Kotlin PID в имени **нет**: имя вида
  `kotlin-daemon.2026-10-20.08-29-00-827.00.log` содержит номер инстанса
  (проверено: живой демон с PID 35498 пишет в лог `…-827.00.log`). Поэтому
  файлы Kotlin группируются по инстансу: живой демон держит открытым только
  последний файл группы (`.NN`), а предыдущие (`.00`, `.01`) лежат на диске —
  открытый файл защищает **всю группу**.

Маркеры Kotlin (`kotlin-compiler-client-*-is-running`,
`kotlin-compiler-in-*.alive`, `kotlin-compilation-session-*-is-running`)
не трогаются никогда: их создаёт и удаляет сам Kotlin, убийство демона их не
оправдывает, а ломать может.

По умолчанию инструмент только показывает план; удаление — по `--apply`.

### Две разные механики чистки логов

Их легко спутать — и легко получить не то, что хотел:

| механика | что делает | с кем работает | риск | как включить |
|---|---|---|---|---|
| `tools/prune-logs.py` | **удаляет** логи | с **мёртвыми** демонами | низкий: лог живого демона открыт процессом — он защищён | вызов инструмента (по умолчанию dry-run) |
| `TRIM_IDLE_LOGS` | **усекает** лог | с **живыми** простаивающими демонами | выше: это запись в чужой файл | `TRIM_IDLE_LOGS=1` в конфиге |

Первое — уборка мусора (файлы, которые всё равно никто не прочитает).
Второе — освобождение места у живого демона, который продолжает писать в тот
же файл: демон Gradle в простое пишет ~124 Б/с (~10 МБ в сутки), и уровнем
логирования это не лечится. Логи Kotlin-демонов не трогает ни одна из двух
механик: у них mtime лога — сам признак простоя.

### Прицельный режим

`PID_ALLOWLIST=1234,5678` в конфиге ограничивает убийство перечисленными PID:
остальные демоны видны в отчёте, но никогда не трогаются. Нужен для первого
боевого прогона и для проверок на поддельных демонах.

## Метрики

**Качество** (нужно для перехода в kill-режим): для каждого «would kill»
следим, не понадобился ли демон снова в течение `REUSE_WINDOW_SECONDS` (6 ч).
Считаем по уникальным PID (плюс starttime, чтобы переиспользованный PID не
считался тем же демоном). Критерий перехода в kill-режим: доля ≤ 60 % при
≥ 8 наблюдённых событиях (`PILOT_MIN_EVENTS`, `PILOT_MAX_REUSE_RATE` — оба
настраиваются конфигом). Вердикт по этому критерию даёт `--pilot`.

У события есть **исход**, и их четыре — это важно, потому что иначе метрика
врёт в обе стороны:

| исход | что значит | в знаменатель |
|---|---|---|
| `reused` | демон понадобился снова | да (ложное срабатывание) |
| `not_reused` | не понадобился | да (верное срабатывание) |
| `unknown` | мы не видели демона часть окна (машина выключена, таймер молчал) | **нет** |
| `killed` | демон реально убит — «понадобился снова» мы уже не увидим | **нет** |

Без `unknown` разрыв наблюдения (машина выключена на ночь) закрывал бы
события как «не понадобился снова» — доля ложных срабатываний была бы
занижена, а вердикт ложнооптимистичен. Без `killed` в kill-режиме доля
выглядела бы идеальной именно потому, что демонов убили.

Источник событий — **отчёт исполнителя**, а не список решений: исполнитель
режет кандидатов (лимит за свип), и то, что он не выполнил, событием не
считается.

Порог событий снижен с 15 до 8 не из «мягкости», а из-за новых порогов
простоя: события Gradle-стороны по замыслу редки (3 из 893 демонов), и
основной вклад даёт Kotlin (2 ч). При старом критерии вердикт по пилоту был
бы недостижим не из-за качества правил, а из-за их строгости.

**Смена правил обнуляет метрику.** Метрика измеряет поведение конкретных
правил; когда правила меняются (`RULES_VERSION`), накопленные события
измеряют уже другое, поэтому метрика сбрасывается автоматически, а рейпер
пишет об этом в вывод свипа.

**Эффект**: `freed_mb` — фактически освобождённая память (по убитым демонам),
`would_free_mb` — сколько могло бы быть освобождено в dry-run.

**Аудит убийств**: каждое фактическое убийство пишется в
`~/.local/state/java-reaper/kills.jsonl` — одна JSON-запись на убийство
(pid, действие, причина, footprint, время). Это журнал для разбора
инцидентов и для месячного отчёта.

**Наблюдаемость правил**: правило «зависший клиент» (соединение висит дольше
`PEER_MAX_AGE_SECONDS`) снимает защиту с демона. Оно влияет на решения, но
раньше не измерялось; теперь срабатывания считаются (`stale_peer_events`) и
показываются в `--status` и `--pilot`.

**Наблюдаемость правил**: каждое решение помнит имя сработавшего правила, в
состоянии лежит гистограмма срабатываний (накопленная и за последний свип) —
видно в `--status` и `--json`. Без неё деградация детекции выглядит как
обычное «нечего было убивать».

**Детекция деградации**: если измерить удалось меньше половины демонов (все
ушли в «неизвестная история» / «нет baseline») или их число упало больше чем
вдвое относительно прошлого свипа — предупреждение в отчёте, в журнале свипа
и ненулевой код возврата `--health`. Раньше замечался только нулевой набор
демонов.

**История решений**: `~/.local/state/java-reaper/sweeps.jsonl` — по одной
строке на свип: сколько демонов видели, сколько памяти висело под ударом
(`would_free_mb`), какие правила срабатывали. В отличие от `state.json`
(последнее состояние) это ИСТОРИЯ: по ней видно, как менялась картина.

**Здоровье**: `--health` сравнивает время последнего свипа с интервалом: если
свипа не было или он старше двух интервалов — «таймер молчит». Это отличает
«нечего было убивать» от «рейпер не работает».

## Протокол пилота (шаг 4 выкатки) — выполнен

Пилот проведён на изолированной паре (Gradle 8.14.6 + Kotlin 2.4.21 в отдельном
`GRADLE_USER_HOME=/tmp/reaper-pilot/.guh`), чтобы не затрагивать чужую работу.

| наблюдение | результат |
|---|---|
| `kill -TERM <gradle-pid>` | Gradle-демон вышел за 5 с |
| лог Gradle-демона | `Daemon vm is shutting down... The daemon has exited normally or was terminated in response to a user interrupt.` |
| клиентский маркер Kotlin | удалён shutdown-hook'ом (файл исчез) |
| Kotlin-демон | через 1 с сам написал `No more clients left` → `Delayed shutdown in 1000ms` → `Shutdown complete` |
| SIGKILL | не потребовался |

Вывод: при штатном SIGTERM Kotlin-демон **не осиротевает** — цепочка
«Gradle-демон → маркер клиента → Kotlin-демон» рвётся корректно. SIGKILL в
инструменте нужен только для демонов, чей клиент умер нечисто (маркер уцелел).

## Тесты

```bash
python3 -m unittest discover -s tests      # 251 тест
```

- `tests/test_reaper.py` — юнит-тесты: разбор логов и таймстемпов, классификатор
  (защиты, эскалация зависшей сборки, least fixed point по peer'ам), метрика,
  конфиг, состояние, поиск лога через `/proc`, CLI.
- `tests/test_policy.py` — инвариантные тесты: перебор случайных сочетаний
  признаков с проверкой «защищённый ⇒ не kill» и «kill ⇒ выполнены все
  условия», детерминированность, лимит убийств за свип, уборка логов.
- `tests/test_kill_path.py` — сквозные тесты kill-пути на поддельных демонах:
  SIGTERM, эскалация до SIGKILL (Gradle — после `GRADLE_SIGKILL_AFTER_TRIES`,
  Kotlin — всегда), dry-run не сигналит, allowlist не трогает чужие PID,
  убийство попадает в `kills.jsonl`. Реальные демоны машины тестами не
  затрагиваются.
- `tests/test_reporting.py` — отчётность и состояние: golden-фикстура из
  настоящего лога Gradle, версия схемы JSON, миграция состояния, round-trip
  возраста peer-соединений, счётчик «зависшего клиента», журнал убийств,
  вердикты `--pilot`/`--audit`/`--explain`, ветки `--health`.
- `tests/test_proc_scan.py` — прицельный поиск владельца сокета: на настоящих
  loopback-соединениях проверяется, что нужный inode находится, а лишние
  процессы не обходятся зря.
- `tests/test_tools.py` — сторож (заметить «молчание» и починить), месячный
  отчёт (цифры сходятся с журналом убийств) и уборка логов (живой демон

  неприкосновенны, dry-run ничего не удаляет).

## Чего инструмент не делает

Не трогает репозиторий проекта и `gradle.properties`, клиентские маркеры
Kotlin, логи живых демонов, процессы чужих пользователей, настройки swap/zram.
Не убивает ничего, кроме Gradle/Kotlin-демонов. Маркеры клиентов не удаляет
никогда: у живого клиента `bootRun` маркер держится сутками, и удаление оборвало
бы сессию компиляции.

Исключение — **уборка логов** (`TRIM_IDLE_LOGS`, по умолчанию выключено):
усекается лог Gradle-демона, простаивающего дольше `TRIM_AFTER_SECONDS`.
Это единственная запись в чужие файлы, и она включается явно.
